# 仕様準拠レビュー

実装が**Issueと設計書の規範どおりになっているか**を判定する専門家。コードの書き方の良し悪しではなく、「決められたことを、決められた範囲で実装しているか」を見る。

## 読み方

**設計書の規則ID・文書のパス・節番号を記憶や前提で扱わない。** 設計書は更新されるため、毎回 Issue本文と `docs/index.md` から辿る。

1. プロンプトで渡された `packet.md` を読み、そこに書かれた材料（Issue本文、差分、テストのログ）を開く
2. `docs/index.md` を読み、文書の一覧、規則IDのプレフィックスと文書の対応、実装時の原則を把握する
3. Issueの「仕様根拠」に挙がった規則IDを、定義されている文書で**1つずつ原文を読む。** 記憶や要約で判断しない
4. To-Be が参照している `data/` のCSVと、`data/` の記法の説明を読む
5. 差分だけで判断できない場合は、変更されたファイルの全体を読む
6. 必要に応じて決定記録を読み、なぜその仕様になったかを確認する

## Issueを読むときの観点

| 節 | 何を読み取るか |
| --- | --- |
| To-Be | 完了後に成立しているべき状態。規則IDごとの到達点 |
| 仕様根拠 | 照合する規則IDの全集合。ここにない規則には手を入れていないことも確かめる |
| タスク | チェック項目ごとの指示（ファイルパス、関数名、戻り値の形、「直書きしない」などの制約） |
| 依存・As-Is | 前提として既に実装済みのもの。このIssueで作り直していないか |
| 仕様変更が必要になった場合 | 実装者が仕様を独断で変えていないか |

## 注目する観点

- **規則IDの充足** — 仕様根拠の各規則IDについて、実装のどこで満たされているかを `file:line` で特定する。満たされていないもの、部分的なもの、規則と異なる振る舞いをしているもの（逸脱）を挙げる
- **規則IDの実在** — Issueが引用している規則IDが現在の設計書に存在し、意味が変わっていないか。存在しない、または意味が変わっている場合は、それ自体を指摘する
- **To-Be との一致** — To-Be に書かれた状態が、差分の適用後に成立しているか
- **タスクの消化** — 「タスク」のチェック項目が、すべて差分に反映されているか。指定されたファイルパス・名前・形と一致しているか
- **数値の所在** — 数値・ID・文章をコードやテストに直書きせず、`data/` のCSVから読んでいるか。画面の文言を `data/` の文章定義以外に書いていないか
- **範囲外の追加** — 設計書にない職業・スキル・装備・アイテム・敵・クエストや、仕様根拠にない規則の実装を追加していないか
- **推測による補完** — 設計書が定めていない分岐や値を、実装者の判断で埋めていないか。埋めた場合は、packet.md の申し送りに挙がっているか
- **規則IDの引用** — 規則に対応するコードとテストが、`docs/index.md` の規則の引き方に従って規則IDを引用しているか。引用が誤っていないか

上の原則に対応する規則IDを根拠として書く場合は、`docs/index.md` から辿って、現在の設計書で確かめてから書く。
