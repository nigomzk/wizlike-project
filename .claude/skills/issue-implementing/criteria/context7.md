# Context7の運用

Godotのエンジン仕様に関わる判断は、**記憶や思い込みではなく、Context7で引いた Godot 4.5 の公式ドキュメントを根拠にする。** メインエージェント（手順3）と `architecture-reviewer`（手順5）の両方が従う。

---

## 1. 参照先

| 項目 | 値 |
| --- | --- |
| ライブラリID | `/websites/godotengine_en_4_5`（プロジェクトの Godot 4.5.1 に対応する） |
| 予備 | `/godotengine/godot-docs/__branch__4.5`（上のIDで見つからない場合だけ使う） |
| 使わないもの | 4.6、4.7、`stable` など、ほかの版の資料。版によってAPIや挙動が違うため |

ライブラリIDは固定なので、`resolve-library-id` は使わずに `query-docs` へ直接渡してよい。

---

## 2. 確認が必須になる判断

| 対象 | 例 |
| --- | --- |
| エンジンのAPI | メソッドのシグネチャ、戻り値、引数の既定値、非推奨かどうか、使えるクラス |
| ノードとリソースの挙動 | `_ready` / `_enter_tree` / `_exit_tree` の順序、`queue_free` の時期、シグナルの接続と切断、`Resource` の共有と複製、`SceneTree` の振る舞い |
| プロジェクト設定 | `project.godot` の設定キーと値（表示、ストレッチ、レンダラー、Autoload、入力マップ） |
| インポート | `.import` の設定、インポーターの種類、テクスチャやフォントの扱い |
| コマンドライン | `--headless` / `--script` / `--import` / `--quit` などの引数、`OS.execute`、終了コード |
| GDScriptの言語仕様 | 静的型付け、`class_name` と Autoload の名前の衝突、`@export` / `@onready`、型付きの配列と辞書、ラムダ、`await` |
| UIとテーマ | `Control` のアンカーとサイズフラグ、フォーカスと入力の伝播、`Theme`、`CanvasLayer` |
| ファイル入出力 | `FileAccess` / `DirAccess` / `ConfigFile`、`user://` の解決、renameの挙動 |

### 確認しなくてよいもの

`Array.append`、`Dictionary.get`、`String.format`、四則演算、`for` / `match` の基本構文のように、版による違いがなく、誤用しても直後のテストで必ず分かるもの。

迷ったら確認する。

---

## 3. 確認の手順

1. 確認したい概念を**1つに絞って**問い合わせる。複数の概念を1回に混ぜない
2. 問い合わせ文に、プロジェクトのコードや固有名、秘密情報を含めない。一般的な概念として尋ねる（例：「Autoload の名前と同じ class_name を持つスクリプトの扱い」）
3. 結果の出典URL（`docs.godotengine.org/en/4.5/...`）を確認する。4.5 以外の版のURLは根拠にしない
4. 結論を、`templates/context7-log.md` の形で調査ログに記録する

---

## 4. 結果の扱い

| 状況 | 扱い |
| --- | --- |
| ドキュメントと自分の想定が食い違った | **ドキュメントに従う。** 想定していた書き方を採らない |
| ドキュメントに記述が見つからない（3回問い合わせても該当なし） | 「未確認」として記録する。メインエージェントは、その判断をテストで裏付けられるならテストで確かめ、そうでなければPR本文の「未確認の事項」に載せる |
| Context7が使えない（接続エラーなど） | 推測で進めない。使えなかったことを記録し、該当する判断を「未確認」としてPR本文に載せる |
| 技術設計の文書とドキュメントが矛盾する | 実装を止め、矛盾の内容を提示して判断を仰ぐ |

---

## 5. レビューでの扱い（architecture-reviewer）

- Godotに関わる指摘には、根拠欄に**出典URL**を書く
- ドキュメントで裏付けられない指摘は **must にしない。** 重大度は should 以下にし、指摘内容に「未確認」と明記する
- 調査ログに記録がないまま、確認が必須の対象に当たるAPIを使っている箇所は、それ自体を should として指摘する。使い方が誤っていることをドキュメントで確認できた場合は must とする
