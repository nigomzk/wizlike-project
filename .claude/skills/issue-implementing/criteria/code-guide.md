# コード解説の資料の基準

手順8-2で `code-explainer` が、PRで追加・変更した `.gd` の解説を書くときに従う。資料の読み手は **Python を扱えるが、GDScript と Godot は初めて扱うユーザー**で、PRのレビューの補足として読む。

---

## 1. 対象のファイル

| 対象 | 扱い |
| --- | --- |
| このPRで追加した `.gd`（`tests/` を除く） | ファイル全体を、節（関数と宣言部）に分けて解説する |
| このPRで変更した既存の `.gd`（`tests/` を除く） | 変更した行を含む節だけを解説する |
| `tests/` 配下の `.gd`（追加・変更とも） | 解説しない。節も、関係図の箱も、読む順も作らない |
| 削除した `.gd` | 解説しない |
| `.tscn`・`.tres`・`project.godot` など | 節を立てない。`.gd` の解説から「`%Back` は `scenes/ui/placeholder.tscn` の `Back` ノード」のように参照するだけにする |

---

## 2. 解説の対象にするコード（3分類）

次の3分類のどれかに当たるコードにだけ、行の注釈を付ける。**どれにも当たらない汎用のロジック（`if` の条件の中身、四則演算、代入、`for` の回し方など）には注釈を付けない。**

| 分類 | `category` | 対象 | 例 |
| --- | --- | --- | --- |
| 言語 | `language` | GDScript の言語仕様のうち、**Python の知識では読めない書き方**。判定は2-1の表で行う | `@onready`・`@export`、`%Name`（シーン内のユニーク名）、`$Path`、`:=` の型推論、`&"..."`、`signal` の宣言、`as`（失敗すると `null`）、`await` でシグナルを待つ書き方 |
| エンジン | `engine` | Godot のエンジン仕様。ノード・シーン・入力・UIの振る舞い | `_ready` / `_unhandled_input` などの仮想メソッドが呼ばれる時機、シグナルの `connect` / `emit`、`call_deferred`、`queue_free`、フォーカスと入力の伝播、`mouse_filter`、`get_viewport()`、`SceneTree` |
| 設計 | `design` | このプロジェクトの設計書が決めている構造と、その理由 | 画面が状態を持たず `setup(flow)` で GameFlow を受け取る（ARC-204）、入力の遮断を GameFlow が理由の集合で持つ（FLW-204） |

- `criteria/context7.md` で Context7 の「確認が必須」に当たるものは、必ず言語かエンジンの注釈にする。ただし言語は2-1で「解説しない」とされたものを除く
- 同じ行が複数の分類に当たる場合は、分類ごとに注釈を分けてよい
- コード中のコメントが既に十分に説明している設計の意図でも、規則IDの意味が初学者に伝わらない場合は設計の注釈を付ける

### 2-1. 言語の注釈を付けるかどうかの表

読み手は Python を扱える。言語（`language`）の注釈と用語集の項目は、次の表で付けるかどうかを決める。**Python の仕様は調べない。表と自分の知識だけで決める。**

| 判定 | 対象 | 該当する書き方 |
| --- | --- | --- |
| 解説しない | Python と見た目も意味も同じ、または意味が自明 | `if` / `elif` / `else` / `for` / `while` / `break` / `continue` / `pass` / `return`、`and` / `or` / `not`、算術・比較・`in`、`func` による関数定義の骨格、`x: int` の型注釈と `-> Type`、`var` / `const` の宣言、`class`（入れ子の内部クラス）、`self`、`true` / `false` / `null`、`[]` と `{}` のリテラル、`#` と `##` のコメント、メソッド名から意味が分かる呼び出し（`append`、`size`、`keys` など） |
| 必ず解説する | Python に相当がない | `@onready`・`@export` などの `@` 注釈、`%Name`、`$Path`、`:=`、`&"..."` と `^"..."`、`extends` と `class_name`（ファイル全体が1つのクラスになる）、`signal` の宣言、`preload` / `load`、`enum`、`static`、`get` / `set` を持つプロパティ、`super` |
| 必ず解説する | 見た目は似ているが意味が違う | `as`（失敗しても例外にならず `null` になる）、`is`（型の検査。同一性の比較ではない）、`Array[T]`（実行時に要素の型を検査する）、`await`（シグナルを待つ）、`match`（パターンの書き方が違う）、`func():` のラムダ（外側のローカル変数を値で取り込む） |
| 表にないもの | 上の3行のどれに当たるかを自分で考える | Python で同じ見た目・同じ意味なら解説しない。相当がないか、意味が違うなら解説する。**判断がつかなければ解説する** |

- 表の「必ず解説する」に当たっても、`criteria/known-terms.md` に載っている語は解説しない（読み手が習得済みと判断した語）。スクリプトが検証する
- 表は注釈を付けるかどうかの判定にだけ使う。解説の本文に Python との対比は書かない（7）
- ラムダは、外側のローカル変数を使っていない場合は解説しない。使っている場合だけ、値で取り込むことを注釈にする
- 表の「解説しない」に当たる行は、エンジンや設計の注釈を付ける行であっても、言語の注釈は付けない

## 3. 粒度

**節の概要＋要所の行注釈**の二層にする。

| 層 | 書くこと | 長さ |
| --- | --- | --- |
| ファイルの概要（`summary`） | このファイルが何の役割を持ち、ほかのどのファイルとつながるか | 1〜2文 |
| 節の概要（`sections[].summary`） | 何をするか、**いつ誰に呼ばれるか**（エンジンが呼ぶ、シグナルで呼ばれる、`screen_host.gd` の `_show_screen()` から呼ばれる など） | 1〜2文 |
| 行の注釈（`notes[].text`） | **この行で何が起きるか**。概念の一般的な説明は用語集に回す | 1〜2文 |
| 用語集（`glossary[].text`） | 概念の定義、使う理由、つまずきやすい点 | 2〜4文 |

- 節は関数ごとに1つ作る。ファイル先頭の `extends`・定数・変数・シグナルの宣言は、まとめて「宣言部」という名前の節にする
- 関数の間の空行やコメントは、前後どちらかの節に含める。節が行の順に並び、重ならないようにする
- **行の注釈の合計は、変更した行（空行を除く）の3割までを目安にする。** 超えると、スクリプトが警告を出す。同じ概念の2回目以降の注釈、コメントを読めば分かる行の注釈、1つの式の中の細かな注釈は、まとめるか外す。レビューするユーザーが読み切れる量にする

---

## 4. 同じ概念が何度も出る場合

- 概念の説明は**用語集に1回だけ**書く。行の注釈は「この行では何が起きるか」の1文にとどめ、`terms` で用語集の項目を参照する
- 用語集の項目は、言語とエンジンの概念を中心にする。設計の項目は、複数のファイルにまたがる構造（例：「画面と GameFlow の関係」）に限って作ってよい

---

## 5. 全体像（関係図と読む順）

関係図は、**このPRで実行時にどうつながるか**を一目で見るためのもので、すべての呼び出しを網羅する図ではない。

- 箱は、変更した `.gd`（`tests/` を除く）と、それを付けたシーン（`main.tscn` など）を中心にする。コードで生成するだけの補助的なノードは箱にしない
- 矢印は**12本まで**にする。同じ2つの箱の間で同じ向きの呼び出しが複数ある場合は、1本にまとめて `label` にメソッド名を「・」で並べる（3つを超える場合は「`request_new_game()` など4件」のようにまとめる）
- テストのファイルは箱にも矢印にも読む順にも載せない
- 読む順は、依存される側から並べる

---

## 6. 正確さ

初学者は解説をそのまま覚えるため、**誤った解説は解説がないより悪い。**

| 分類 | 根拠 | 根拠がない場合 |
| --- | --- | --- |
| 言語・エンジン | Godot 4.5 の公式ドキュメント（`https://docs.godotengine.org/en/4.5/` 配下）の出典URLを `source` に書く。`context7-log.md` に記録がある事項はその出典を使い、ない事項は `criteria/context7.md` の手順で Context7 に問い合わせる | `unverified: true` を付け、本文に「公式ドキュメントで確認できなかった」と書く。推測を断定の形で書かない |
| 設計 | 根拠の規則IDを `ruleIds` に完全な形で書く（`ARC-204`。`ARC-2xx` や範囲の表記は使わない）。規則の意味は、`docs/index.md` から辿った設計書の原文で確かめる | 設計の注釈にしない |

- 解説は、そのPRの HEAD のコードに対して書く。コードと食い違う説明を書かない
- 実際の挙動をテストや実測で確かめた事項は、その旨を本文に書いてよい（例：「`_initialize` の間はルートがツリーに入らない。公式ドキュメントに記述はなく、テストで確かめた」）。この場合も `unverified: true` を付ける

---

## 7. 書き方

- 日本語で、です・ます調ではなく、設計書と同じ常体（だ・である調）で書く
- **ほかのプログラミング言語との対比を書かない。** GDScript と Godot の用語だけで説明する
- コードの語句は `` ` `` で囲む（HTMLで `code` の書式になる）。そのほかのMarkdownの記法は使わない
- 規則IDは本文に書いてよいが、そのときも `ruleIds` に載せる
