# 指摘の処置基準

メインエージェントが手順6と手順12で、レビュー担当とユーザーの指摘に**修正・見送り・却下・記録のみ**のどれかを決めるための基準。処置は `triage.md` に記録し、PR本文に転記する。

---

## 1. レビュー担当の指摘

上から順に判定する。

| # | 確認すること | 当てはまる場合の処置 |
| --- | --- | --- |
| 1 | 根拠が示されているか。重大度に必要な根拠の種類を満たしているか（`severity.md` §2） | 根拠がない → **却下**。必要な種類を満たしていない → 重大度を1段階下げて続ける |
| 2 | 根拠が正しいか。規則IDの本文、`file:line`、Context7の出典URLを**自分で開いて**確かめる | 根拠が誤っている、または該当箇所が存在しない → **却下** |
| 3 | 別のレビュー担当の指摘と重複していないか | 重複している → 1件にまとめ、重大度は高いほうを採る |
| 4 | 別のレビュー担当の指摘と矛盾していないか | 設計書の記述を正として解消する。解消できなければ、ユーザーに判断を仰ぐ |
| 5 | 対応するには仕様の変更が必要か | 必要 → 実装を止め、理由と影響を提示して判断を仰ぐ |
| 6 | 重大度ごとの処置 | 下の表に従う |

| 重大度 | Issueの範囲内 | Issueの範囲外 |
| --- | --- | --- |
| must | **修正** | **見送り**。理由を記録し、別のIssueにすべき内容としてPR本文に載せる（既存コードの不具合など） |
| should | **修正** | **見送り**。理由を記録する |
| nit | **記録のみ** | **記録のみ** |

### 「Issueの範囲内」の定義

次のすべてを満たす場合を範囲内とする。

- 直す箇所が、このIssueで追加または変更したファイルの中にある。もしくは、Issueの「タスク」に挙がっているファイルの中にある
- 直しても、To-Be と仕様根拠に挙がっていない規則に手を入れることにならない
- 直しても、「壊してはいけないもの」の受入IDが落ちない

## 2. ユーザーの指摘（手順12）

| 状況 | 処置 |
| --- | --- |
| 指摘の意図が明確で、仕様と矛盾しない | **修正**。範囲外に見える場合でも、ユーザーの指示を優先する |
| 指摘の意図が曖昧 | 実装の前に、チャットで1問ずつ確認する |
| 指摘が設計書の規則と矛盾する | 実装を止め、矛盾する規則IDを示して判断を仰ぐ。指摘に従う場合は、Issueに `type:spec-change` が必要になる可能性を伝える |
| 手動確認で見つかった不具合 | 再現手順を整理し、可能なら自動テストを先に書いて失敗を確認してから直す |

ユーザーの指摘は、**却下も見送りもしない。** 対応できない理由がある場合は、処置を決めずにユーザーに相談する。

---

## 3. 記録の形

`triage.md` とPR本文には、`templates/pr-body.md` の「指摘の処置」表の形で記録する。却下・見送り・記録のみの指摘も、すべて理由を添えて残す。
