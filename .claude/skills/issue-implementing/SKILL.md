# Issue実装スキル

`/issue-drafting` で起票したIssueを、**仕様根拠の規則IDとDoDの受入IDを満たす実装**に落とし、PRとして提出する。ユーザーのPRレビューでOKが出るまで繰り返す。

対象リポジトリは `nigomzk/wizlike-project`。設計書は `docs/`、固定データは `data/` にある。

### 設計書の引き方

このスキルとレビュー担当は、設計書の**規則ID・文書のパス・節番号を前提にしない。** 設計書は更新されるため、必要な規則と文書は毎回次の2つから辿る。

- **Issue本文** — 仕様根拠の規則ID、DoDと壊してはいけないものの受入ID、確認方法のコマンド、参照すべき画面文書
- **`docs/index.md`** — 文書の一覧、規則IDのプレフィックスと文書の対応、受入IDの索引の所在、決定記録の所在

このスキルに書かれた原則（数値は `data/` を正とする、設計書にないものを追加しない、推測で仕様を補わない、未実施を完了としない など）に対応する規則IDが必要な場合も、`docs/index.md` から辿って引用する。

## 全体の流れ

| 手順 | 内容 | 担当 |
| --- | --- | --- |
| 0 | モード判定 | メイン |
| 1 | Issueを読む | メイン |
| 2 | 開発用ブランチを作成する | メイン |
| 3 | 実装する（TDD、Context7で確認） | メイン |
| 4 | commitする | メイン |
| 5 | レビューを依頼する | 専門サブエージェント（並列） |
| 6 | 妥当な指摘を修正する | メイン |
| 7 | 4〜6を再実施する（**レビュー依頼は1サイクルにつき最大2回**） | メイン＋専門 |
| 8 | pushする | メイン |
| 9 | PRを作成する | メイン |
| 10 | ユーザーがPRの修正内容を確認し、Godotで動作を確認する | ユーザー |
| 11 | ユーザーがレビュー指摘を出す（指摘がなければ完了） | ユーザー |
| 12 | 3〜11を再実施する（ユーザーのレビューでOKが出るまで） | メイン＋専門 |

**サイクル**は、初回実装（手順1〜9）を1回目とし、手順12でユーザーのレビューに対応するたびに1つ増える。手順5の回数制限は、サイクルごとに数える。

### 作業ファイルの置き場所

レビューの材料やテストのログは、セッションのスクラッチパッドのディレクトリ（ない場合はOSの一時ディレクトリ）に置く。**リポジトリ内には置かない。**

```
<scratchpad>/issue-<N>/
  context7-log.md            # 調査ログ（全サイクル共通で追記）
  cycle-<c>/
    test-red.log             # テストを先に書いたときの実行結果
    test-green.log           # 実装後の実行結果
    round-<r>/
      packet.md              # レビュー依頼の材料（templates/review-packet.md）
      issue.md               # Issue本文
      diff.patch             # git diff main...HEAD
      test-latest.log        # このラウンド直前の実行結果
      id-table.md            # 規則IDと受入IDの一覧の下書き（PR本文に転記する）
      findings-<agent>.md    # 各レビュー担当の出力
      triage.md              # 指摘の処置表
```

### テストの実行

**実行コマンドは、Issueの「確認方法」に書かれたものを使う。** このスキルにはコマンドを固定しない。受入IDを指定する引数だけを、下の規則で組み替える。初回の実行に事前の手順（インポートなど）が必要かどうかは、README の実行手順に従う。

Godotの実行ファイルは環境変数 `GODOT` で指す。未設定の場合は推測せず、ユーザーにパスを確認する。リポジトリに絶対パスを書かない。

結果は、標準出力と標準エラーをログファイルに保存し、終了コードも記録する。

| シェル | 書き方 |
| --- | --- |
| PowerShell | `<確認方法のコマンド> *> <ログのパス>; $LASTEXITCODE` |
| Bash | `<確認方法のコマンド> > <ログのパス> 2>&1; echo "exit=$?" >> <ログのパス>` |

受入IDの指定に含めるのは、**自動検証の受入ID**だけである。手動確認の受入IDは含めない。どの接頭辞が自動検証でどれが手動確認かは、`docs/index.md` から受入IDの索引を辿って、実行時に判定する。

## 手順

### 0. モード判定

引数としてIssue番号 `N` を受け取る。番号がなければユーザーに確認する。

```bash
gh issue view N --repo nigomzk/wizlike-project --json number,title,state,labels
git fetch origin --prune
git branch -a --list "*/N-*"
gh pr list --repo nigomzk/wizlike-project --state all --head <見つかったブランチ名> --json number,headRefName,state,url
```

ブランチ名は `{type}/{N}-{slug}` なので、`*/N-*` に一致するブランチを探し（`remotes/origin/` の接頭辞は外す）、そのブランチを head にもつPRを探す。

| 状態 | モード | 進み方 |
| --- | --- | --- |
| ブランチもPRもない | **初回モード** | 手順1から |
| ブランチはあるがPRがない | **再開モード** | 手順1を行ったあと、ブランチの差分とコミットから進み具合を把握し、ユーザーに状態を報告してから続きを進める |
| OPENのPRがある | **レビュー対応モード** | 手順12へ |
| PRがMERGEDまたはCLOSED、またはIssueがCLOSED | — | 状態を報告して止まる |

### 1. Issueを読む

1. `gh issue view N --repo nigomzk/wizlike-project --json title,body,labels,comments` で、本文・ラベル・コメントを読む
2. 「依存」節にあるIssueが、すべてCLOSEDになっているか確認する。未完了のものがあれば、**着手せずにユーザーに確認する**
3. `docs/index.md` を入口にして、次の文書を辿って読む
   - 「仕様根拠」の規則IDが定義されている文書（該当する節）
   - DoDの受入IDが定義されている文書と、受入IDの索引・テストの規約
   - 画面を扱うIssue（`area:ui`）では、「確認方法」や To-Be に挙がっている画面文書と、全画面に共通する表示の規約
   - To-Be が参照している `data/` のCSV
   - 必要に応じて決定記録
4. 次のどれかに当たれば、**実装を始めずにユーザーの判断を仰ぐ**
   - 設計書どうしの矛盾が解消できない
   - Issueの記述と設計書が食い違っている（Issueが引用している規則IDが存在しない、または意味が変わっている場合を含む）
   - 画面文書の未決事項が残っている
   - `type:spec-change` が付いている。この場合は、実装の前に行う `docs/` の更新と決定記録への記録の内容を提示し、承認を得る

### 2. 開発用ブランチを作成する

作業ツリーがクリーンであることを確認する。クリーンでなければ、ユーザーに確認する。

```bash
git switch main
git pull --ff-only
git switch -c {type}/{N}-{slug}
```

| 要素 | 決め方 |
| --- | --- |
| `{type}` | Issueの `type:` ラベルの値（`feat` / `test` / `chore` / `spec-change`） |
| `{slug}` | Issueタイトルの要旨を表す英語。小文字のケバブケースで2〜4語（例：`feat/7-inventory-rules`） |

### 3. 実装する（TDD）

Issueの「タスク」を上から順に進める。**Issueに書かれていないもの（職業・スキル・装備・アイテム・敵・クエスト、新しい規則）を追加しない**。数値は `data/` のCSVから読み、コードやテストに直書きしない。

コードコメントとテストで規則IDや受入IDを引用するときは、**1件ずつ完全な形で書く**（`TST-003, TST-004`。`TST-003, 004` や `TST-001〜006` としない）。既存のコメントの省略表記は、このIssueで変更する行に含まれる場合だけ直す。設計書が規則の群を指す表記（`ARC-1xx` など）は使ってよい。

#### 3-1. Context7で確認する

`.claude/skills/issue-implementing/criteria/context7.md` に従い、**Godotのエンジン仕様に関わる判断は、Context7で確認してから実装する。** 思い込みや記憶で書かない。調べた内容は、`templates/context7-log.md` の形で `context7-log.md` に追記する。

#### 3-2. テストを先に書き、失敗を確認する

1. DoDに挙がった自動検証の受入IDのテストを、設計書のテストの規約が受入IDの接頭辞ごとに割り当てているテストファイルに書く。期待値は `data/` のCSVから算出する
2. DoDの受入IDを指定して実行し、結果を `cycle-<c>/test-red.log` に保存する
3. 対象のIDが**失敗・スキップ・実行不能**のいずれかであることを確認する。テストを書いた直後に成功した場合は、そのテストが何も検証していない疑いがあるため、テストを見直す

DoDが手動確認の受入IDだけのIssueでは、`test-red.log` に「自動検証の対象なし」と記録する。ただし、ルール層やサービスの変更を含む場合は、その部分のテストを先に書く。

#### 3-3. 実装して、成功を確認する

1. タスクに書かれたファイルパスに実装する
2. **DoDの受入ID＋「壊してはいけないもの」のうち自動検証のID**を指定して実行し、結果を `cycle-<c>/test-green.log` に保存する。終了コード0を確認する
3. 受入IDを指定せずに全体を実行し、失敗が0件であることを確認する
4. 実装中に仕様の変更が必要になった場合は、**実装を止め、理由と影響を提示して判断を仰ぐ**

### 4. commitする

変更をまとまりごとにコミットする。**どのコミットでもテストが通る状態を保つ。** `git add -A` は使わず、ファイルを指定して追加する。

```
<type>: <変更の要約（英語、命令形）> (#N)

<必要なら本文>

Co-Authored-By: <セッションの指示に従う>
```

`<type>` は Conventional Commits の値（`feat` / `fix` / `test` / `refactor` / `docs` / `chore`）を使う。レビュー指摘による修正は、内容に応じて `fix` か `refactor` にする。

### 5. レビューを依頼する

#### 5-1. 材料をそろえる

`cycle-<c>/round-<r>/` に次を書き出す。

| ファイル | 内容 |
| --- | --- |
| `issue.md` | Issueの本文（タイトル・ラベル・コメントを含む） |
| `diff.patch` | `git diff main...HEAD` |
| `test-latest.log` | このラウンドの直前に、3-3の2・3と同じ条件で実行した結果 |
| `id-table.md` | 規則IDと受入IDの一覧の下書き。作り方は下の「ID一覧の下書きを作る」 |
| `packet.md` | `templates/review-packet.md` に従う。ほかのファイルのパス、変更ファイルの一覧、前のラウンドの処置表、レビュー対応モードではユーザーの指摘を載せる |

`test-red.log`、`test-green.log`、`context7-log.md` は、packet.md からパスで参照する。

#### ID一覧の下書きを作る

PR本文の「対応した規則ID」節と「受入IDごとの結果」表の下書きを、`templates/pr-body.md` の同じ節と同じ形・同じ書き方の決まりで作る。レビュー担当（`spec-conformance-reviewer`）が設計書と照合し、手順9でPR本文に転記する。

1. **規則IDを集める。** Issueの「仕様根拠」の規則ID、`diff.patch` の追加行（`+` で始まる行）に現れる `PREFIX-NNN` 形式のID、4で作る受入IDの表の「検証する規則ID」列のIDを集める。追加行に省略表記（`TST-003, 004`、`TST-001〜006`）があれば展開して集め、このIssueで書いたコメントであれば手順3の決まりに従って直す。設計書に追加・変更した規則や受入条件の定義行の本文にだけ現れるIDは集めない（定義行そのもののIDは集める）
2. **原文を転記する。** `docs/index.md` から各IDのプレフィックスを定義している文書を辿り、HEAD の文書から、そのIDの行を grep で抜き出して転記する。記憶や要約から書き起こさない。見つからないIDは、規則（要約）に「（設計書に存在しない）」と書いて残し、引用の誤りとして直す
3. **要約と区分、対応ファイルを書く。** 対応ファイルは、追加行でそのIDを引用しているファイルとする
4. **受入IDの表を作る。** DoDと「壊してはいけないもの」の自動検証の受入IDについて、受入IDの索引から手順・期待結果・規則IDを読み、`test-red.log` と `test-latest.log` の結果を添える

2ラウンド目では、修正を反映した差分から作り直す。

#### 5-2. 専門サブエージェントを並列で呼び出す

**1つのメッセージの中で、すべてのAgent呼び出しを同時に発行する。** 順番に呼ばない。

| エージェント | 起動する条件 | 担当 |
| --- | --- | --- |
| `spec-conformance-reviewer` | 常に | 規則IDの充足、`data/` を正とする原則、範囲外の追加の禁止 |
| `test-reviewer` | 常に | TDDの記録、DoDの受入IDの成立、壊してはいけないもの |
| `architecture-reviewer` | 常に | 技術設計の規約、Godot / GDScript の正しさ（Context7で確認） |
| `screen-reviewer` | Issueに `area:ui` が付いているとき | 画面文書との一致、手動確認の手順 |

各エージェントへのプロンプトには、次を書く。

1. `packet.md` の絶対パス（レビュー担当は、そこから材料を読む）
2. 出力の型 `.claude/skills/issue-implementing/templates/review-findings.md` と、判定基準 `.claude/skills/issue-implementing/criteria/severity.md` のパス
3. 「自分の担当の観点に関わる変更がなければ、『該当なし』と判定欄に書くこと」

各エージェントの出力を `findings-<agent>.md` として保存する。

### 6. 妥当な指摘を修正する

`.claude/skills/issue-implementing/criteria/finding-triage.md` に従って、すべての指摘の処置を決め、`round-<r>/triage.md` に記録する。

| 重大度 | 処置 |
| --- | --- |
| must | 根拠を確かめたうえで全件修正する |
| should | Issueの範囲内で直せるものだけ修正する。範囲外のものは見送り、理由を記録する |
| nit | 修正せず、記録だけ残す |
| 根拠のない指摘や根拠の誤り | 却下し、理由を記録する |

テストの不足を指摘された場合は、手順3と同じく、テストを先に書いて失敗を確認してから直す。修正後は3-3の2・3を再実行する。

ID一覧の下書き（`id-table.md`）への指摘は、下書きを直す。リポジトリのファイルではないため、処置表のコミット欄は「—」とする。

### 7. 4〜6を再実施する

| 状況 | 次の手順 |
| --- | --- |
| 全員の判定が「承認」または「該当なし」で、修正もない | 手順8へ |
| このサイクルのレビューが1回目で、手順6で修正した | 手順4に戻り、commitして2回目のレビューを依頼する |
| このサイクルのレビューが2回目 | 手順6の修正をcommitし、手順8へ。**3回目のレビューは依頼しない。** レビューを経ていない修正と、残った must は、PR本文に明記する |

### 8. pushする

```bash
git push -u origin {type}/{N}-{slug}
```

### 9. PRを作成する

`templates/pr-body.md` に従って本文をスクラッチパッドに書き出し、PRを作成する。「Godotでの手動確認」は、`screen-reviewer` の手順案（最後のラウンドのもの）と、Issueの「確認方法」をもとに書く。指摘の処置は、このサイクルのすべてのラウンドの `triage.md` から転記する。

「対応した規則ID」節と「受入IDごとの結果」表は、最後のラウンドの `id-table.md`（手順6で直したもの）から転記する。書き終えたら本文を見直し、次を確かめる。

- 本文に、IDの省略表記が残っていない
- 本文に現れる規則ID（原文の `<details>` の中は除く）が、すべて「対応した規則ID」節の表に載っている。載っていなければ、手順5-1と同じ方法で行と原文を追加する（区分は参照のみ）

```bash
gh pr create --repo nigomzk/wizlike-project --base main --head {type}/{N}-{slug} \
  --title "<Issueのタイトルと同じ>" --body-file <本文のパス> \
  --label "<Issueと同じラベル>" ...
```

### 10. ユーザーに引き渡して止まる

次を報告し、**ユーザーの確認を待つ。** このスキルの中でマージしない。

- PRのURL
- 自動検証の結果（指定した受入IDと終了コード）
- Godotで行ってほしい手動確認（手動確認の受入IDと手順。PR本文と同じもの）
- 未確認の事項（Context7で裏付けられなかった判断）、見送った指摘、残った must

### 11. ユーザーのレビュー

ユーザーはPR上で修正内容を確認し、Godotで動作を確認して、PRのコメントかチャットで指摘する。指摘がなければ、そのIssueは完了とする。

### 12. レビュー対応モード（3〜11を再実施する）

1. ブランチに切り替えて最新にする：`git switch {type}/{N}-{slug}` → `git pull --ff-only`
2. ユーザーの指摘を集める
   ```bash
   gh pr view <PR番号> --repo nigomzk/wizlike-project --json number,url,state,mergeable,reviews,comments
   gh api repos/nigomzk/wizlike-project/pulls/<PR番号>/comments
   ```
   - 最後にpushしたコミットの日時（`git log -1 --format=%cI`）より後に投稿されたものを、未対応の指摘とする
   - このスキルが投稿したコメント（本文に `<!-- issue-implementing:cycle-reply -->` を含むもの）は除外する。ユーザーとこのスキルは同じGitHubアカウントで投稿するため、投稿者では区別できない
   - チャットで指摘を受けた場合は、それも含める
3. 未対応の指摘がない場合は、その旨を報告して止まる。ユーザーが「OK」「指摘なし」と示した場合は、完了を報告して止まる
4. `mergeable` が `CONFLICTING` の場合は、`main` を取り込んで競合を解消し、テストを再実行する
5. 指摘を処置する。**ユーザーの指摘は原則としてすべて対応する。** ただし、仕様と矛盾する指摘や意図が曖昧な指摘は、実装の前にユーザーに確認する
6. サイクル番号を1つ増やし、手順3〜8を行う。レビューの回数は新しいサイクルで0から数える。packet.md にはユーザーの指摘と、その処置を載せる
7. PRの本文の「対応した規則ID」節、「受入IDごとの結果」表、「指摘の処置」節、「サイクルごとの対応」節を更新し（`gh pr edit --body-file`）、`templates/cycle-reply.md` に従ってPRにコメントを投稿する（`gh pr comment --body-file`）
8. 手順10と同じ内容を報告して止まる

## 守ること

| 原則 | 内容 |
| --- | --- |
| Issueの範囲で実装する | タスクとTo-Beに書かれていないものを作らない |
| 数値を直書きしない | 実装でもテストでも、`data/` のCSVから読む |
| 推測で仕様を補わない | 矛盾や仕様変更の必要が見つかったら、止まって判断を仰ぐ |
