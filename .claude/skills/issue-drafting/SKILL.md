# Issue作成スキル

設計書や不具合内容を入力として、**何も知らない実装エージェントが迷わず着手できる**Issueを、適切な粒度で必要な数だけ作成する。

対象リポジトリは `nigomzk/wizlike-project`。設計書は `docs/`、固定データは `data/` にある。

---

## 手順

### 1. 設計書を読む

今回Issue化する対象を読む。対象は次のいずれか、または複数の組み合わせ。

- 設計書そのもの（`docs/` 配下の文書）
- 設計書の改訂差分（`git diff` や、ユーザーが提示した変更内容）
- 新しく追加された設計文書
- 不具合報告・バグの症状・再現手順

あわせて次の2つを必ず読み、文書の地図と決定の経緯を把握する。

- `docs/index.md` — 文書の一覧、規則IDのプレフィックス対応、実装時の原則
- 決定記録（所在は `docs/index.md` から辿る） — なぜその仕様になったか

このスキルとエージェントは、設計書の**規則ID・文書のパス・節番号を前提にしない。** 設計書は更新されるため、必要な規則と文書は毎回 `docs/index.md` から辿る。このスキルに書かれた原則（数値は `data/` を正とする、推測で補わない など）に対応する規則IDが必要な場合も、`docs/index.md` から辿って引用する。

対象が曖昧な場合はここでユーザーに確認する。広すぎる対象（「設計書全部」など）は、そのまま進めず範囲の確認を取る。

### 2. 入力種別を判定する

`.claude/skills/issue-drafting/criteria/scoping-routes.md` を読み、今回の入力が4ルートのどれに当たるかを決める。

| 入力種別 | 判定の目安 |
| --- | --- |
| 初版 | まだ実装が存在しない範囲を、設計書から一括で起票する |
| 改訂差分 | 既存の設計書の規則が変更・追加・削除された |
| 新規文書追加 | 新しい設計文書が増えた |
| 不具合 | 実装済みの挙動が期待と違う |

複数に当たる場合は分けて扱い、それぞれのルートを適用する。

### 3. 専門エージェント7体を並列で呼び出す

**1つのメッセージの中で7つのAgent呼び出しを同時に発行する。** 順番に呼ばない。

| エージェント | 担当 |
| --- | --- |
| `spec-rule-analyst` | 規範の確定（規則ID、As-Is / To-Be） |
| `architecture-decomposer` | 実装単位とタスクへの分解 |
| `data-contract-auditor` | `data/` のCSV契約とバリデータ要件 |
| `acceptance-criteria-designer` | 受入条件IDと確認方法・DoD |
| `ui-requirements-analyst` | 画面・操作・共通UI部品・手動確認 |
| `issue-scope-planner` | 粒度・順序・依存・ラベル |
| `defect-analyst` | 不具合の再現と規則違反としての言語化 |

各エージェントへ渡す情報：

1. 今回の**対象範囲**（対象ファイルのパス、差分の内容、不具合の文面をそのまま）
2. ステップ2で判定した**入力種別**
3. `issue-scope-planner` には、判断基準のパス `.claude/skills/issue-drafting/criteria/` を明示する
4. 「自分の関心事に該当するものが入力に含まれない場合は『該当なし』と1行で返すこと」

エージェントは `Read` しか持たない。差分や不具合の文面など、ファイルとして存在しない情報はプロンプト本文に書いて渡す。

### 4. 結果を集約する

7体の出力を突き合わせ、次を確定させる。

- 実装すべき**規則ID**の全集合（`spec-rule-analyst`）
- それを実装する**実装単位**とファイルパス（`architecture-decomposer`）
- 各実装単位の**受入条件ID**（既存 / 新設）と検証手段（`acceptance-criteria-designer`）
- 先行して必要な **`data/` の追記**（`data-contract-auditor`）
- 画面側の要件と**共通UI部品の再利用**（`ui-requirements-analyst`）
- 不具合の場合は**原因の実装単位と回帰リスク**（`defect-analyst`）

エージェント間で食い違いがある場合は、設計書の記述を正として解消する。

**設計書どうしの矛盾が解消できない場合は、Issueを起票せずユーザーに判断を仰ぐ。** 推測で仕様を補わない。設計書に書かれていない職業・スキル・装備・アイテム・敵・クエストをIssueに混ぜない。

### 5. 粒度を決めてIssueへ割り付ける

`.claude/skills/issue-drafting/criteria/granularity-invariants.md` を読み、**すべてのIssueが不変条件を満たすまで**分割・統合する。`issue-scope-planner` の案を出発点にし、ステップ4で判明した事実と矛盾する場合は調整する。

受入条件IDが存在しない範囲は、`acceptance-criteria-designer` の新設案を採用し、Issueのタスクに「対応する仕様文書への受入条件の追記と、受入IDの索引の更新」を含める。

### 6. Issue草案を書き出す

`templates/` に型がある場合はそれに従う。ない場合は下記の構成で書く。Issue 1件＝1ファイルとして、スクラッチパッドへ出力する。

```
## 概要
## As-Is（現状）
## To-Be（あるべき姿）
## タスク
- [ ] 上から順に実行できる単位で列挙する
## 確認方法
## DoD
## 仕様根拠
## 壊してはいけないもの
## 仕様変更が必要になった場合
```

各節の書き方：

| 節 | 内容 |
| --- | --- |
| 概要 | 1〜3文。このIssueで何が動くようになるか |
| As-Is | 現在の実装状態。未実装なら「未実装」と明記。不具合なら実測の挙動 |
| To-Be | 完了後の状態を**規則IDを引用して**書く。数値は書かず `data/` のCSVを指す |
| タスク | 触るファイルパスを明示したチェックボックス。実装順に並べる |
| 確認方法 | ヘッドレスなら実行コマンドと対象テストファイル、実機確認なら手順 |
| DoD | 通すべき受入条件ID。新設の場合は「新設」と明記 |
| 仕様根拠 | 実装する規則ID。連続する場合は範囲で書いてよい（例：`<PREFIX>-300〜<PREFIX>-308`） |
| 壊してはいけないもの | 既に通っている受入条件ID |
| 仕様変更が必要になった場合 | 実装を進めず、理由と影響を提示して判断を仰ぐ |

Issueに必ず記載する項目は、`docs/index.md` から辿れる「Issueの共通要件」で定められている。草案を書く前にその文書を読み、上の構成に不足があれば補う。

### 7. 一覧を提示して承認を待つ

次の一覧を出し、ユーザーのOKを待つ。**承認前に `gh` を実行しない。**

| # | タイトル | area | type | 含む規則ID | DoDの受入ID | 依存 |

あわせて、分割・統合の理由、新設が必要な受入条件、先行して必要な `data/` の追記を短く添える。

### 8. 発行する

承認後、`gh issue create` で `nigomzk/wizlike-project` へ起票する。ラベルは、`docs/index.md` から辿れる「Issueの共通要件」の定めに従い、`area:` と `type:` を1つ以上ずつ付ける。使える値は `gh label list --repo nigomzk/wizlike-project` で確かめる。共通要件にあってリポジトリに存在しないラベルは、作らずにユーザーに確認する。

`type:spec-change` が付くIssueは、本文の先頭に「実装の前に `docs/` の該当IDを更新し、決定記録に理由を記録する」と明記する。

依存関係がある場合は、発行後に本文へ依存先のIssue番号を追記する。最後に発行したIssueのURL一覧を返す。

---

## 守ること

| 原則 | 内容 |
| --- | --- |
| 規則IDで書く | 仕様の内容を言い換えず、規則IDで引用する |
| 数値を複写しない | 数値は `data/` のCSVが唯一の正 |
| 推測で補わない | 設計書にない仕様をIssueに書かない |
| 検証できない状態で閉じない | 受入条件IDを持たないIssueを作らない |
| 設計書の構成を前提にしない | 規則ID・文書のパス・節番号は、毎回 `docs/index.md` から辿って確かめる |
| 承認前に発行しない | 草案の確認を必ず挟む |
