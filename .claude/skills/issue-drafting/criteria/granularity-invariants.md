# 粒度の不変条件

入力の種類によらず、**すべてのIssueが次の3つを満たす**。満たさないIssueは分割または統合する。

---

## 不変条件

### 1. 単一の責務単位に閉じている

1つのIssueが触る中心は、技術設計の文書が定める責務の1つ、1画面、1データ層など、**1つの単位**であること。

- 1つのIssueで、戦闘のルールとセーブの処理と商店の画面のように、別々の責務を同時に触らない
- 複数の単位にまたがる場合は、単位ごとに分割し、依存関係で順序を付ける
- ただし、その単位を動かすために不可分な周辺の修正（呼び出し元1箇所の接続など）は含めてよい

### 2. 完了を判定できる受入条件IDを1件以上持つ

受入IDの索引（`docs/index.md` から辿る）にある受入条件IDを、**既存または新設で1件以上**持つこと。

- 既存IDで判定できるなら、そのIDをDoDに書く
- 判定できるIDが存在しないなら、新設IDを提案し、対応する仕様文書への追記と索引の更新をタスクに含める
- 新設も立てられない（＝完了を客観的に判定できない）場合、そのIssueは切り方が間違っている。判定できる単位まで分割するか、判定できる他のIssueへ統合する
- 基盤整備など受入条件IDに馴染まない作業は、成果物の存在と実行結果（例：「テストが終了コード0で完了する」）を検証手段として明記する

### 3. 単独で入れても既存の受入条件IDを壊さない

そのIssueだけをマージしても、**既に通っている受入条件IDが落ちない**こと。

- 落ちる可能性のあるIDは「壊してはいけないもの」に列挙する
- 落とさずに入れられない場合は、先に土台を作るIssueを分けて依存させる
- 中間状態でビルドが通らない切り方をしない

---

## 分割・統合の判断材料

不変条件を満たしたうえで、次に該当したら**分割を検討**する。

| 兆候 | 理由 |
| --- | --- |
| DoDの受入条件IDが5件を大きく超える | 1回の実装で閉じにくく、レビュー単位として大きい |
| 複数のマイルストーンにまたがる | 実装順序の前提が揃っていない |
| 仕様根拠の規則IDが3系統以上のプレフィックスにまたがる | 関心事が混ざっている |
| タスクに「〜したうえで、別途〜」が現れる | 2つの作業が同居している |
| ヘッドレス検証と、配布物の実機検証が同居している | 検証のサイクルが違う |

次に該当したら**統合を検討**する。

| 兆候 | 理由 |
| --- | --- |
| 単独では受入条件IDを1件も持てない | 不変条件2を満たせない |
| 同じファイルを連続して触るだけのIssueが並ぶ | 分割のコストが利益を上回る |
| 片方をマージしても何も動かない | 中間状態で検証できない |

---

## 書かないこと

- **Issueの総件数の目安を規則にしない。** 設計書は改訂・追加され続ける。件数を固定すると、差分開発や文書追加のときに粒度が歪む
- **特定のマイルストーン名や文書名を条件に埋め込まない。** 判断は不変条件と上記の兆候のみで行う
