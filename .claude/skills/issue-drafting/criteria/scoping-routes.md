# 切り出し起点の4ルート

`granularity-invariants.md` の不変条件は全入力に共通する。**どこから切り始めるか**だけが入力の種類で変わる。

---

## ルート判定

| 入力種別 | 判定の目安 |
| --- | --- |
| A. 初版・新規実装 | 対象範囲にまだ実装が存在せず、設計書から一括で起票する |
| B. 改訂差分 | 既存の設計書の規則が変更・追加・削除された |
| C. 新規文書追加 | 新しい設計文書が増え、既存の文書群に接続する必要がある |
| D. 不具合 | 実装済みの挙動が設計書の規範と食い違っている |

複数に当たる場合は分けて扱い、それぞれのルートを適用したうえで、最後に重複するIssueを統合する。

---

## A. 初版・新規実装

**起点：責務単位 × マイルストーン**

1. 対象範囲に関わる規則IDを全部集める
2. `tech/architecture.md` の責務（ARC-3xx）とディレクトリ（ARC-1xx）へ写像し、実装単位の一覧を作る
3. `plan/milestones.md` の段階で並べ、依存の順序を付ける
4. 実装単位ごとに、判定できる受入条件IDを割り当てる
5. 不変条件を満たすまで分割・統合する

注意：

- 共通の土台（データ層、共通UI部品、テスト基盤）を、それを使う機能Issueより前に置く
- `data/` のCSVに値が無いものは、データ整備のIssueを先に立てる
- 縦スライス（プレイヤーから見て動く単位）と、ヘッドレスで検証できるルール層は分けてよい。ルール層のIssueは表示を待たずに完了できる（`ARC-004`）

---

## B. 改訂差分

**起点：変更・追加・削除された規則IDの集合**

1. 差分から、**変わった規則IDを列挙**する（新規追加 / 内容変更 / 削除・欠番化）
2. 各規則IDについて、それを実装している（するはずの）実装単位を特定する
3. 実装単位でグルーピングし、1グループ＝1Issueを起点にする
4. その規則に紐づく**既存の受入条件IDが今も成立するか**を確認する
   - 成立しなくなる → 受入条件の更新をタスクに含める
   - 成立する → 「壊してはいけないもの」に入れる
5. 不変条件を満たすまで分割・統合する

注意：

- **削除された規則**も起票対象。実装から該当の挙動を取り除くIssueを立てる。欠番化した規則IDを実装が参照したまま残さない
- 差分が仕様そのものの変更なら `spec-change` ラベルを付け、`docs/` の更新と `decisions/log.md` への記録を実装の前段タスクに置く
- 影響範囲を決めつけない。規則IDを全文検索し、参照している箇所をすべて洗う

---

## C. 新規文書追加

**起点：その文書の規則ID群 → 責務単位への写像**

1. 新しい文書の規則IDを、ブロック（100刻み）単位でまとめる
2. Aと同様に責務単位へ写像し、実装単位の一覧を作る
3. **既存文書との接続点を別Issueとして切り出す**
   - 既存の状態モデル・セーブ形式・画面遷移に足される項目
   - `schema_version` / `content_version` への影響（`GLS-5xx`）
   - 既存の受入条件IDへの影響
4. 受入条件IDが未整備なら、索引（`tech/testing.md`）への追加をタスクに含める
5. 不変条件を満たすまで分割・統合する

注意：

- 新規文書の内部だけで閉じるIssueと、既存に食い込むIssueを混ぜない。後者のほうが回帰リスクが高く、レビューの観点が違う
- 用語・ID体系が既存と衝突していないかを先に確認する（`GLS-4xx`）

---

## D. 不具合

**起点：違反している規則ID／単一の原因ごとに1件**

1. 期待される挙動の**出典となる規則ID**を特定する
2. 実測との差を書く。再現手順は、状態・入力・乱数系列（`GLS-2xx`）まで含めて書く
3. **仕様不備か実装不備かを判別する**
   - 実装不備 → 修正Issue。`type: feat` または `chore`
   - 仕様不備（規則がそもそも矛盾・未定義）→ `type: spec-change`。`docs/` の更新と `decisions/log.md` への記録を先行タスクに置く
4. **原因が同じものは1件にまとめる。症状が複数でも原因が1つなら1Issue。** 逆に、症状が1つでも原因が独立して複数あるなら分ける
5. 再発防止の受入条件IDを新設し、DoDに入れる。既存IDで捕まえられなかった＝テストの穴なので、原則として新設する
6. 回帰リスクのある受入条件IDを「壊してはいけないもの」に列挙する

注意：

- 原因が特定できない場合は、修正Issueではなく**調査Issue**として起票する。DoDは「原因の特定と、再現する受入条件の提示」とする
- 「ついでに直す」を混ぜない。関係のない改善は別Issueにする
