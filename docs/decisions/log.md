# 決定記録

仕様がなぜ現在の形になったかの記録。**規範的な内容は含まない。** 実装時に参照するのは `spec/` と `tech/` であり、本文書は仕様と矛盾が見つかった場合に、元の意思決定を照合するために用いる。

## 6. 文書構成の切り直し（2026-09-21）

Issue駆動での実装に向けて、4文書構成から `spec/` + `tech/` + `data/` 構成へ切り直した。

### 動機

1. 決定記録と規範的な仕様が同一文書に同居しており、実装時に不要な文脈を読む必要があった。本文書がその決定記録にあたる。
2. 規則にIDがなく、Issue・テスト・コードから特定の規則を引用できなかった。
3. 数値がMarkdownの表に置かれていたため、バランス調整を開始した時点で仕様と乖離することが確定していた。数値の正を `data/` のCSVへ移した。
4. 1つの機能の規則が3文書に分散しており、1つのIssueで複数文書の横断を要した。

### 方針

既存の文章を再導出せず、移動・分解・採番による変換とした。すべての規則は元の文に由来を持つ。旧文書と旧構成は git 履歴の `c92c357` 時点に、変換の差分は `07b363e` に残る。

### 変換時に加えた仕様変更

| # | 変更 | 理由 |
| --- | --- | --- |
| 1 | 敵の単体対象の抽選タイミングを「実行確定時」から「ターン解決の開始時（実行確定の直後）」へ明確化（BTL-602） | 「実行時に死亡していれば変更する」という別の規則と2文字違いで意味が異なり、取り違えると再照準が機能しないため。乱数順序の記述が前者の解釈を支持していた |
| 2 | 「残り歩数」を「遭遇残り歩数」と「忍び足の残り効果歩数」に分離（GLS-308, GLS-309） | 同一の語が2つの別の値を指しており、実装で取り違える危険があったため |
| 3 | B01の期待値の定義を、固定値から「`data/` と式から算出した期待値」へ変更 | バランス調整でデータを変更した際に、テストが仕様の誤りとして落ちることを防ぐため |
| 4 | パーティ0人を、登録者0人の場合に限定した（PTY-102, PTY-103, TWN-110, SAV-402） | 「街では0人を許容する」と「無効なパーティは拒否する」が両立していなかったため。下記の補足を参照 |
| 5 | 商店の品揃えの解禁条件を `ConditionDef` で表すことを明記（TWN-236, DAT-226） | クエストの解禁条件と同形であるのに判定方式が未指定で、二重実装になる恐れがあったため |
| 6 | アイテムの回復量が使用者のTECを加算しないことを明記（INV-403） | スキルの回復式との違いが明示されていなかったため |
| 7 | `content_version` が `0.x` の間はセーブ互換を保証しない運用を明記（GLS-503, SAV-502） | 開発中はほぼ毎Issueで破壊的変更が起きるため、都度バージョンを上げる運用が成立しないため |
| 8 | 受け入れ条件を追加（B08〜B10, E06〜E08, I05〜I07, P01, P02, Q01〜Q07, S05, F05, F06, FL01〜FL04, D03, D04） | 仕様に明記されているのに検証手段がない規則が多数あったため。新しい規則は導入していない |
| 9 | 僧侶の蘇生スキルが教会の蘇生をほぼ代替する点を、意図的な許容として明記（TWN-702） | 抜け穴として放置されていたため。仕様は変更せず、許容として記録した |

#### 補足：パーティ0人の扱い（変更4）

当初は「パーティ0〜4人を有効としてロードを受理する」としたが、レビューを経て次の方針へ変更した。

パーティが0人であってよいのは登録者が0人の場合に限る。これはニューゲーム直後から最初の登録までの間にのみ発生する。この間はギルド以外の施設・出発・セーブを利用できないため、パーティ0人のセーブデータは生成されない。

登録者が1人以上いる場合、パーティは常に1〜4人とする。編成画面で最後の1人を外す操作は拒否し、入れ替えは「先に追加してから外す」で行う。登録と編成が別操作である以上、登録の有無だけをゲートにしても「登録済みだがパーティ未編成」の状態でセーブできてしまうため、パーティ側にも下限を置いた。

削除によってパーティが0人になり、かつ他に登録者が残る場合は、その削除を拒否する。最後の登録者を削除した場合のみ、登録者0人・パーティ0人の初期状態へ戻る。

登録者0人の間は、メニューも開けないこととした（TWN-110）。メニューの7項目のうち所持品・装備・スキル・能力・地図の5つが対象0人になり、特に所持品はニューゲーム支給の消耗品が存在する一方で使用対象が0人という状態を作る。これを禁止することで「メニューを開ける時点で登録者は1人以上いる」という不変条件が成立し、各画面の空リスト分岐と0対象ガードが不要になる（TWN-113）。

この状態でも「タイトルへ戻る」はTOWNの直下にあるため、閉じ込めは発生しない。

一方で、設定画面への経路がメニューのみであったため、このままでは登録前に音量とフルスクリーンを変更できなくなる。そこでTITLEに「設定」を追加し、TITLEとMENUの両方から同一の設定画面を開けることにした（FLW-001, FLW-014, FLW-111）。設定は `user://settings.cfg` に進行とは別に保存され、5スロットで共有されるため、セッションが存在しないTITLEからでも安全に開ける。閉じると必ず呼び出し元へ戻す（FLW-113）。

## 7. 文書構成の見直し（2026-10-03）

Issueの起票を始める前に、文書を横断して読む負担を減らすため構成を見直した。規則IDは振り直していない。削除した規則IDは欠番とした（GLS-001）。

### 動機

1. 同じ規則が複数の文書に言い回しを変えて書かれていた。たとえば登録者0人の扱いは11か所に書かれていた。突き合わせの負担が大きく、修正時に一部を直し忘れて矛盾が生じる危険があった。
2. タイトル・街・ギルド・メニュー・セーブスロットなどの画面に、表示項目・選択可否・遷移先を定義する場所がなかった。画面を1つ実装するために5文書以上を拾い読みする必要があった。
3. 実装の順序が `plan/milestones.md` に書かれており、Issueの運用を始めるとGitHubと二重管理になる状態だった。
4. 画面の文言が仕様文書の本文に直接書かれており、PRS-702（文章は `data/texts.csv` が唯一の正）と矛盾していた。

### 変更

| # | 変更 | 理由 |
| --- | --- | --- |
| 1 | 1つの規則を1か所でのみ定義し、他の文書からは「この文書が扱わない範囲」の表で参照する方式にした | 動機1 |
| 2 | 「初回版に含めないもの」はSCP-3xxのみを正とし、各文書での再掲を削除した | 動機1 |
| 3 | `spec/screens/` を新設し、画面ごとに遷移・表示・操作・文言・未決事項・手動確認を置いた。PRS-2xxは各画面文書へ移した | 動機2 |
| 4 | 画面の手動確認の受入ID `U01〜U33` を新設した。WはWindows実機での通し試験として残した | 画面Issueの完了をIDで判定するため |
| 5 | TITLEの遷移を検証する受入ID FL07を新設した | タイトル画面のIssueに自動検証の手段がなかったため |
| 6 | システムメッセージとエラーコードの表示文を `data/texts.csv` へ移し、仕様文書からはIDで参照するようにした | 動機4 |
| 7 | ARC-1xxに不足していたシーン（設定、起動不可のエラー、文章画面、出発先、メニューの下位画面）を追加した。FLとEのテストファイルを分離した | 画面一覧と構成図の不一致、テストファイルの担当の不自然さを解消するため |
| 8 | `plan/milestones.md` を段階A〜Hと共通要件のみに縮め、順序を「画面で確認できる範囲が広がる順」に組み替えた。Issueの順序はGitHubのMilestonesで管理する | 動機3。セーブは登録者が必要なためギルドの後に、施設は戦闘の後に置いた |

#### 検知方式の比較

| 案 | 概要 | 補助関数内の打ち切り | 契約の変更 | 結果 |
| --- | --- | --- | --- | --- |
| c | `OS.add_logger` と `Logger._log_error` で、`run()` の実行中のスクリプトエラーを検知する | 検知できる | なし | **採用** |
| b | `const IDS` を Dictionary にして、IDごとの期待 `check` 回数を宣言させる | 検知できる（回数不足） | 全テストファイルの `IDS` が変わる。ループで回数が変わるテストの保守が重い | 不採用 |
| a' | IDごとの開始・終了のマーカー（`t.begin(id)` / `t.end(id)`） | 検知できる | 全テストファイルに記述が増える | 不採用 |

#### 案 c の確認結果

Godot 4.5.1 のヘッドレス `--script` で、最小のスクリプトを用いて確かめた。

- `null` へのメソッド呼び出しによる実行時エラーは、`run()` から呼んだ補助関数の中で起きても `Logger._log_error` に届く。エラーの後も呼び出し元は続行する
- `error_type` は、スクリプトの実行時エラーが `ERROR_TYPE_SCRIPT`（2）、`push_error` が `ERROR_TYPE_ERROR`（0）、`push_warning` が `ERROR_TYPE_WARNING`（1）で、スクリプトの実行時エラーだけに絞れる
- 公式ドキュメント（Godot 4.5、`Logger` と `OS.add_logger`）によれば、`_log_error` は複数のスレッドから呼ばれうるため、排他制御（`Mutex`）が必要
