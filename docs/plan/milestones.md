## 2. 依存関係

実装順序は「動作確認可能な縦スライス」の順であり、依存関係そのものではない。

```
M0 → M1 → M2 → M3 → M4 ─┐
              └─→ M5 ────┼→ M7
              └─→ M6 ────┘
```

| 規則 | 内容 |
| --- | --- |
| 並行可 | M5（ダンジョン）とM6（戦闘）はM1の完了後に並行して着手できる。`BattleSession` と `BattleRules` はヘッドレスで検証できるため、ダンジョンの完成を待たない（ARC-004）。 |
| M4の位置 | M4はM3に依存する（所持品と装備の容量判定を使うため）が、M5・M6とは独立している。 |
| M7の位置 | M7はM4・M5・M6のすべてに依存する。 |

---

## 3. M0を独立させる理由

顔画像10枚はM3の冒険者作成で必要になり、日本語フォントは最初の画面から必要になる。テスト基盤がなければM1の完了を判定できない。共通UI部品を先に作らなければ、13画面で同等の実装を重複させることになる（ARC-207）。これらをM7へ後置しない。

## 4. Issueの共通要件

各Issueに次の4項目を必ず記載する。

1. **仕様根拠** — 実装する規則のID（例：`BTL-300〜BTL-308`）
2. **受け入れ条件** — 通すべきテストID。存在しない場合は「新設」と明記し、対応する仕様文書にも追記する
3. **壊してはいけないもの** — 既に通っている受け入れ条件ID
4. **仕様変更が必要になった場合** — 実装を進めず、理由と影響を提示して判断を仰ぐ（SCP-402）

### ラベル

| 種別 | 値 |
| --- | --- |
| area | `data` / `save` / `town` / `party` / `inventory` / `dungeon` / `battle` / `quest` / `ui` / `test` / `build` |
| type | `feat` / `test` / `chore` / `spec-change` |

`spec-change` は仕様そのものの変更を伴うIssueに付ける。このラベルが付いたIssueは、実装の前に `docs/` の該当IDを更新し、`decisions/log.md` に理由を記録する。
