# 実装の段階

Issueを置くための段階と、全Issueに共通する要件を定義する。**個々のIssueの順序と進捗はGitHubのMilestonesとIssueで管理する。** 本文書にIssueの一覧を書かない。

---

## 1. 段階

各段階は、完了した時点でGodotを起動して確かめられる範囲が広がる順に並べる。各段階の完了条件は、担当する受入IDがすべて通ることとする。

| 段階 | 名前 | 主な内容 | 完了条件（受入ID） |
| --- | --- | --- | --- |

| B | データ | 定義Resource型、`data/` のCSVの読込、バリデータ、起動不可のエラー画面 | D01, D03, U07 |

## 2. 依存関係

```
A → B → C → D → E → F → G → H
         └─────→ F（ルール層のみ）
```

| 規則 | 内容 |
| --- | --- |
| 段階の順序 | 上表の順に着手する。後の段階の機能を、前の段階の確認のために先取りしない。 |
| ルール層の先行 | `BattleRules`・`BattleSession`・`GrowthRules` は画面なしで検証できるため（ARC-004）、Bの完了後であればEを待たずに着手してよい。戦闘画面はEの後とする。 |
| セーブの位置 | Dは登録者が1人以上いることを前提とするため（SAV-300）、Cの後に置く。E以降の動作確認では、保存したデータからの再開を利用する。 |
| 施設の位置 | 宿屋と教会は戦闘で減ったHPと状態を戻す施設であるため、Fの後に置く。 |

## 3. Issueの共通要件

各Issueに次の5項目を必ず記載する。

1. **仕様根拠** — 実装する規則のID（例：`BTL-300〜BTL-308`）。画面を実装するIssueは、該当する画面文書（`spec/screens/`）も示す
2. **受け入れ条件** — 通すべき受入ID。存在しない場合は「新設」と明記し、対応する仕様文書にも追記する
3. **確認方法** — 画面を伴うIssueは、Godotでの手動確認（`U` の受入ID）の手順を書く。ルール層のみのIssueは、テストの実行コマンドと、終了コードが0になることを書く
4. **壊してはいけないもの** — 既に通っている受入ID
5. **仕様変更が必要になった場合** — 実装を進めず、理由と影響を提示して判断を仰ぐ（SCP-402）。画面文書の未決事項が残っている場合は、着手前に解消する

### ラベル

| 種別 | 値 |
| --- | --- |
| area | `data` / `save` / `town` / `party` / `inventory` / `dungeon` / `battle` / `quest` / `ui` / `test` / `build` |
| type | `feat` / `test` / `chore` / `spec-change` |

`spec-change` は仕様そのものの変更を伴うIssueに付ける。このラベルが付いたIssueは、実装の前に `docs/` の該当IDを更新し、`decisions/log.md` に理由を記録する。
