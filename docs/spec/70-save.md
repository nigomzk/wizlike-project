# セーブ・ロード

セーブファイルの配置、形式、保存手順、読込時の検証、障害対応を定義する。

**この文書が扱わない範囲**

| 関心事 | 所在 |
| --- | --- |
| 保存対象となる状態モデルの構造 | `tech/data-model.md`（DAT-5xx） |
| 未保存の確認ダイアログ | `spec/10-flow.md`（FLW-3xx） |
| スロット一覧画面のレイアウト | `tech/presentation.md` |
| 設定の保存（`user://settings.cfg`） | `tech/presentation.md`（PRS-4xx） |

## 1. 方針（SAV-0xx）

| ID | 規則 |
| --- | --- |
| SAV-000 | セーブは街での手動操作のみとする。 |
| SAV-001 | スロットは5つとする。 |
| SAV-002 | 上書きの前に確認を表示する。 |
| SAV-003 | 「はじめから」の選択とNEW_GAMEは、既存のセーブスロットに一切触れない。 |
| SAV-004 | 全滅、アプリの終了、ニューゲームの開始のいずれでも自動保存しない。 |
| SAV-005 | スロットの一覧には、保存日時、ゲーム内日数、パーティ、クリア済みかどうかを表示する。 |
| SAV-006 | スロット表示用の別マニフェストを作らない。本体のファイルから読む。 |

## 2. ファイルと形式（SAV-1xx, SAV-2xx）

| ID | 規則 |
| --- | --- |
| SAV-100 | 本体を `user://saves/slot_01.json` 〜 `slot_05.json` に置く。 |
| SAV-101 | 同じフォルダーの `.tmp` を一時ファイル、`.bak` をバックアップとして用いる。 |
| SAV-102 | 書込み先を `res://` にしない。 |

JSONの外枠（SAV-110）。

```json
{
  "schema_version": 1,
  "content_version": "0.1.0",
  "engine_version": "4.5.1",
  "saved_at_utc": "ISO-8601 UTC",
  "scene": "town",
  "session": {}
}
```

| ID | 規則 |
| --- | --- |
| SAV-111 | `session` には `GameSession` の永続フィールドをすべて含める（DAT-5xx）。 |
| SAV-112 | `Vector2i` は `[x, y]` の配列、`StringName` は文字列、Resourceへの参照はIDとして保存する。 |
| SAV-113 | HPが0であることを死亡の唯一の根拠とする。別の `dead` 真偽値を保存しない。 |
| SAV-114 | JSONの整数は、読込時に整数であることと値域を検証する。 |
| SAV-200 | 乱数のseedとstateは、64bit精度の喪失を避けるため、数値ではなく10進文字列として保存する。 |
| SAV-201 | 復元ではseedを先に設定し、その後にstateを設定する。 |
| SAV-202 | stateはRNGから取得した値のみを保存する。独自に計算した値を保存しない。 |
| SAV-203 | 探索中の位置（`ExplorationState`）は保存しない。街でのみ保存するため、常にnullとなる。 |
| SAV-204 | `BattleSession` は保存しない（BTL-906）。 |

## 3. 保存手順（SAV-3xx）

| ID | 手順 |
| --- | --- |
| SAV-300 | TOWNであり、登録者が1人以上おり、モーダルの取引・戦闘・探索のいずれも進行していないことを検証する。上書きの確認後、状態を不変のDTOへコピーする。 |
| SAV-301 | DTOを検証し、`.tmp` へJSONを書き込み、flushとcloseを行い、読み戻してパースと検証を行う。 |
| SAV-302 | 既存の本体がある場合、その有効性を確認したうえで `.bak` へ退避する。退避の各段階のエラーを検査する。 |
| SAV-303 | 無効な本体の上書きをユーザーが選んだ場合、無効なデータで有効なバックアップを置き換えない。 |
| SAV-304 | `.tmp` を本体へrenameする。失敗した場合はバックアップから本体への復元を試み、`save_failed` を表示する。 |
| SAV-305 | 保存に失敗した場合、メモリ上の進行を保持し、未保存フラグを立てたままにする。 |
| SAV-306 | 書込みと置換の両方が成功した場合にのみ `save_done` を表示し、未保存フラグを解除する。 |
| SAV-307 | 初回の保存に失敗してバックアップが存在しない場合も、再試行できるようメモリ上の進行を保持する。 |
| SAV-308 | OSとファイルシステムのあらゆる障害に対して完全な原子性を保証したと表現しない。各段階の失敗を個別にテストし、有効な旧データまたはバックアップから復帰できる状態を保つ。 |

## 4. 読込と検証（SAV-4xx）

| ID | 規則 |
| --- | --- |
| SAV-400 | 本体をパースして検証したうえで新しい `GameSession` を組み立て、完全に成功した場合にのみ現在のセッションと置き換える。 |
| SAV-401 | 次のいずれかに該当する場合は拒否する。書式の不正、未知のID、参照切れ、冒険者の重複、無効なパーティ、レベルと経験値の不一致、範囲外の座標、HPとSPの不正、日数の不正。 |
| SAV-402 | パーティは1〜4人を有効とする。0人、5人以上、IDの重複、存在しないIDの参照を無効とする。 |
| SAV-403 | `schema_version` または `content_version` が異なる場合は `save_incompatible` を表示し、自動変換しない（GLS-503）。 |
| SAV-404 | 本体が欠落または破損しており、同一スロットの `.bak` が有効である場合、`save_backup_available` を表示して選択させる。 |
| SAV-405 | 自動的に別のスロットを読み込まない。`.tmp` を自動的にロードしない。 |
| SAV-406 | 有効なデータが存在しないスロットを `save_slot_empty` と `save_slot_unreadable` で区別して表示する。 |
| SAV-407 | ロードに失敗した場合もファイルを削除しない。 |
| SAV-408 | ロード後はTOWNの通常画面から再開する。マップの記録、クエスト、冒険者、魔法陣、ボスの撃破日、乱数の状態をすべて復元する。 |

## 5. 版の管理（SAV-5xx）

| ID | 規則 |
| --- | --- |
| SAV-500 | `data/` のIDまたは数値テーブルを破壊的に変更した場合、`content_version` を更新する。 |
| SAV-501 | 仮マップの地形の変更も、座標の意味が変わるため破壊的変更として扱う。 |
| SAV-502 | `content_version` が `0.x` の間は旧セーブとの互換を保証しない。ロードに失敗した場合は `save_incompatible` を表示し、`user://saves/` を削除して続行する運用とする。 |

## 6. 受け入れ条件

| ID | 前提・操作 | 合格条件 | 根拠 |
| --- | --- | --- | --- |
| S01 | 5スロットへ異なる進行を保存する | それぞれ独立してロードでき、名前・日数・探索記録・乱数の状態まで復元される | SAV-111, 408 |
| S02 | JSONを途中で切断する、未知のIDを含める、旧versionにする | いずれも拒否し、ファイルを保持する。有効な `.bak` があれば選択できる | SAV-401, 403, 404, 407 |
| S03 | `.tmp` の書込み、`.bak` への退避、renameにそれぞれ失敗を注入する | 保存成功を表示しない。メモリ上の進行と、復元可能な旧データを保持する | SAV-301〜307 |
| S04 | 全滅する、アプリを終了する、ニューゲームを開始する | いずれも自動保存せず、既存の5スロットを変更しない | SAV-003, 004 |
| S05 | パーティ0人、5人以上、重複IDを含むセーブデータをロードする | いずれも拒否される。1〜4人のみ受理する | SAV-402 |
| S06 | 登録者0人の状態でセーブを試みる | セーブできない。スロットは変更されない | SAV-300, TWN-110 |
